# 期間環境レポート

SV Match Log Web に蓄積されたランクマ戦績から、管理者向けに選択期間の環境レポート用の集計データを作成する機能です。

## 管理画面URL

- `/admin/weekly-report`

既存の管理者認証を使用します。`admin_users` に登録されていないユーザーは閲覧できません。

## 集計ルール

環境分布と使用デッキ勝率は、基準にするデッキを明確に分けています。

- 環境分布・遭遇率: `matches.opponent_archetype_id` を優先し、未設定時は `opponent_deck_id` を使います。
- 使用デッキ別勝率: `matches.my_archetype_id` を優先し、未設定時は `my_deck_id` を使います。

「対戦相手として多く当たったデッキ」は、ユーザー自身が多く使用したデッキではありません。

## 期間の定義

期間レポートは、画面で選択した開始日から終了日までを Asia/Tokyo の日付境界で集計します。終了日未指定の場合は、従来互換として開始日から7日間で集計します。

例:

- 選択期間: `2026-08-27 00:00:00` から `2026-09-04 23:59:59`
- 前期間: `2026-08-18 00:00:00` から `2026-08-26 23:59:59`

DBの `played_at` がUTCで保存されていても、画面で選んだ日本時間の日付からUTC境界へ変換して問い合わせます。

## データ信頼度

閾値は `src/lib/weekly-report-config.ts` で管理します。

- 9戦以下: サンプル不足
- 10から19戦: 参考値
- 20戦以上: 十分なサンプル

使用デッキ勝率ランキングと主要対面の初期最低試合数は10戦です。

## 期間比較の信頼度

選択期間と、その直前にある同じ日数の前期間の総試合数から `comparisonConfidence` を判定します。

- `high`: 選択期間・前期間とも300戦以上、かつ少ない方が多い方の50%以上
- `medium`: 選択期間・前期間とも150戦以上
- `low`: それ以外

例として、選択期間750戦・前期間105戦の場合は `low` です。`low` の場合、管理画面では前期間比較を参考値として表示します。前期間0戦または前期間全体のサンプルが少ない場合は、「新規デッキ」と断定せず「選択期間確認」「前期間未確認」に近い扱いにします。

使用デッキ勝率の前期間比較は、選択期間・前期間の両方が `MIN_WINRATE_COMPARISON_MATCHES` 相当の10戦以上ある場合のみ通常の変化として扱います。対面勝率の前期間比較も、選択期間・前期間の両方が10戦以上の場合のみ通常の対面変化として扱います。

## Tier候補ロジック

Tierは確定値ではなく候補です。

候補:

- Tier1
- Tier1.5
- Tier2
- Tier3
- 評価保留

判定では、使用デッキ勝率、試合数、主要対面成績、前期間比較、信頼度を中心に参照します。設定値は `src/lib/weekly-report-config.ts` に分離しています。

### Strength Score と Meta Presence

Tierは「強さ」の暫定評価です。遭遇率はデッキパワーそのものではないため、Tier評価では大きく加点しません。

- `Strength Score`: 使用時勝率、主要対面成績、サンプル信頼度、直近トレンドから算出する強さ指標
- `Meta Presence`: 対戦相手としての遭遇率・遭遇数から見る環境存在感

これらは内部計算・管理用の指標です。通常のTier表、PNG出力、AI compact payload では表示・送信せず、読者向けには勝率、試合数、遭遇率、主要対面勝率を使います。

初期重み:

- 使用時勝率: 45%
- 主要対面成績: 35%
- サンプル信頼度: 15%
- 直近トレンド: 5%

`Meta Presence` は以下の3段階です。

- High
- Medium
- Low

使用者側勝率と、統合対面データから見た対象デッキ勝率に大きな差がある場合は「データ乖離あり」として評価保留候補にします。

## 対面勝率の統合

`A使用 vs B` と `B使用 vs A` は、デッキIDをソートした1組の対面として統合します。

出力項目:

- `deckA`
- `deckB`
- `totalMatches`
- `deckAWins`
- `deckBWins`
- `deckAWinRate`
- `deckBWinRate`

既知の制約として、現在のDBには同一試合を一意に結びつける共通試合IDがありません。同じ試合を双方のユーザーが登録した場合、それを自動で二重計上除外することはできません。

## 主要対面の計算方法

主要対面は `majorMatchupMinMatches` 以上、初期値では10戦以上の統合対面です。

Tier判定に使う `weightedMajorMatchupWinRate` は、各対面の試合数を重みとした加重平均です。これにより、30戦の対面と5戦の対面を単純に同じ重みで平均しません。

## 環境相関図条件

初期条件:

- 対面10戦以上
- 有利側勝率55%以上

相関図の矢印は「有利側 → 不利側」です。参考値は点線の枠で表示します。

## AI compact payload とプロンプト

OpenAI APIキーの有無に関係なく、管理画面から以下をコピーできます。

- AIへ渡す集計済みJSON
- note本文生成用プロンプト

AI用JSONは記事生成用に軽量化した compact payload です。管理画面表示用の集計データは保持しつつ、AIへ渡すJSONには原則として以下だけを含めます。

- 対象期間
- 選択期間総試合数
- 前期間総試合数
- `comparisonConfidence`
- データ品質警告
- 遭遇率TOP12
- ランキング対象になった使用デッキ勝率
- 有効な前期間変化
- 最終Tier
- 主要対面
- 相関図データ
- データ利用上の注意

少数試合の大量デッキ一覧はAI payloadから除外します。数値はAI向けには原則小数1桁に丸めます。`Strength Score` と `Meta Presence` は内部指標のためAI payloadには含めません。

以下は含めません。

- メールアドレス
- ユーザー名
- ユーザーID
- 認証ID
- IPアドレス
- 個人単位の戦績
- 生の戦績行

## 有料note構成

AIプロンプトは、有料note向けに無料部分と有料部分を分ける構成です。

無料部分:

- 選択期間の環境まとめ
- ランクマで多く当たったデッキTOP5
- 選択期間の重要ポイント

有料部分:

- 使用デッキ別勝率
- 前期間からの変化
- 選択期間のTier表
- 注目対面
- 環境相関図から見るメタ
- 選択期間で注目したいデッキ
- 次に注目したいポイント
- データについて

## 運営者メモ

管理画面には「運営者メモ」欄があります。

入力した内容はAIプロンプトへ「運営者の所感」として追加されます。統計データとは別扱いにし、AI記事でも「データ上」と「運営者の所感」が混ざらないよう指示しています。未入力でも正常に動作します。

## OpenAI API設定

API本文生成を使う場合は、サーバー側の環境変数に設定します。

```env
OPENAI_API_KEY=sk-...
OPENAI_WEEKLY_REPORT_MODEL=gpt-4.1-mini
```

`OPENAI_WEEKLY_REPORT_MODEL` は任意です。未設定時は `gpt-4.1-mini` を使用します。

APIキーはサーバーアクション内だけで使用し、クライアントHTMLやJavaScriptへ露出しません。

## API未設定時の使い方

`OPENAI_API_KEY` が未設定でも、以下は利用できます。

- 期間集計
- 前期間比較
- Tier候補
- グラフ表示
- PNG保存
- 環境相関図
- AI用JSONコピー
- AI用プロンプトコピー

本文生成だけが無効になり、画面に「OPENAI_API_KEY 未設定」と表示されます。

## 操作方法

1. `/admin/weekly-report` を開きます。
2. 開始日と終了日を選びます。
3. 各セクションのPNGボタンで画像を保存します。
4. AI用JSONまたはAI用プロンプトをコピーします。
5. 必要に応じてTier手動調整と運営者メモを入力します。
6. APIキー設定済みの場合は「AI本文生成」を押してMarkdown本文を生成します。
7. 生成本文をコピー、または `period-report-YYYY-MM-DD_YYYY-MM-DD.md` として保存します。

## 必要な環境変数

既存:

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- `NEXT_PUBLIC_SITE_URL`

任意:

- `OPENAI_API_KEY`
- `OPENAI_WEEKLY_REPORT_MODEL`

## 既知の制約

- DB変更なしで実装しているため、集計は既存の `matches` と `deck_archetypes` に依存します。
- 同一試合が複数ユーザーから登録された場合の二重計上は判定できません。
- 管理画面のTierは現時点では候補表示です。永続保存や手動上書き保存は未実装です。
- Tierの手動調整はAI用JSON/プロンプトには反映されますが、DBには保存しません。
- AI生成本文は保存しません。必要な場合はコピーまたはMarkdown保存してください。
- 大規模データでは、さらにSQL RPCで集計をDB側へ寄せる余地があります。
