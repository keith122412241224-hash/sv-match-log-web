## F. セキュリティと個人情報管理

**Googleとログ。** Googleの識別子、確認状態を含むメール・基本プロフィールをSupabase Authが会員IDに関連付ける。GoogleのパスワードはGoogleに入力し、アプリはログイン用セッションを使用する。Google API用のproviderトークン2種は既存処理がセッション保存前に除外する。本番認証基盤のアクセスログには期限付きの認証値が残り得る。障害確認は件数・時刻帯・結果に絞る。閲覧者と転送先の定期確認、保存期限の記録、疑いがある場合のアクセス制限・事故判断を管理者が行う。今回の確認に生ログや認証値は使用していない。

**手動のAI評価。** スナップショット生成は内部で戦績・投稿者IDを参照し、寄与の集中などを計算する。個々の会員IDやメールを構造化出力に加える処理は見当たらない。出力に含む環境・デッキ・評価実行等の識別子は会員IDと区別する。前回評価・調査プラン・参照URL等の自由入力や、少数件の組み合わせには個人と結び付く余地がある。毎回、送信前に確認し、識別できる資料は保留。手動運用の過去の全入力について送信ゼロとは判定していない。個人情報を含む状態でAIに渡す運用へ切り替える際は、目的、委託・提供の法的根拠、契約・利用者説明を先に見直す。法令上の「匿名加工情報」の認定はしていない。[ChatGPTのデータコントロール](https://help.openai.com/en/articles/7730893-data-controls-in-chatgpt)

**アクセス解析。** 既存SDKはページURLを受け取り、公開配信スクリプトはフィルター適用後に参照元を別フィールドに追加できる。元の実装にはアプリ側の送信制限がなかった。過去の認証情報の流出件数は未確認。今回の変更は既知の固定パスだけを許可し、クエリ・断片を常に除外、未知のパス・カスタムイベント・識別情報を含み得る参照元はイベントごと除外する。ブラウザーの参照元ポリシーは原則オリジンのみ、既存の認証コールバックはより厳しい `no-referrer` を維持。認証・管理画面の閲覧数と一部の流入元は計測されなくなる。管理画面で生URLを検索する必要はない。ホスティング側のアクセスログ・過去の解析履歴には遡及しない。[Vercel Web Analyticsの仕様](https://vercel.com/docs/analytics/privacy-policy)・[送信前の除外方法](https://vercel.com/docs/analytics/redacting-sensitive-data)

**退会・その他の請求の受付手順。**

1. 正式メールで希望する手続きを受ける。受付時は登録有無を第三者に伝えない。通常は登録先への個別返信と本人からの応答で所有を確かめる。既にログインした本人による確認等も事案に応じて検討し、登録先を失った場合は別経路で本人性を確立できるまで開示・削除を保留する。パスワード、ログインリンク、Cookieの提出を求めない。
2. 開示・訂正等と退会とを区別し、必要な対象だけを特定する。退会なら削除範囲と復元の可否を説明し、本人の意図を再確認する。依頼番号、本人確認方法、処理対象・結果を最小限で記録する。
3. アプリの管理画面には本人確認から退会完了までを行う機能がない。権限のある運営者がSupabaseの管理機能で対象会員を一意に照合する。スキーマ上、認証ユーザーからプロフィール・本人戦績・所有デッキ・提案・管理者登録・所有環境等への連鎖削除があり、一部の作成者参照はNULLになる。**共有環境・共有デッキや他会員の参照がある場合は操作を止め、影響と引き継ぎを個別承認する。** Storageの所有物、他スキーマ、過去の集計・公開資料、手元の問い合わせメールも個別に確認する。一般会員を一般化して管理者アカウントに同じ操作を適用しない。
4. 対象と影響を確認できた場合のみ、対象依頼の承認を得て手動対応し、個別データ・関連行の結果と他会員への影響を確かめて登録先に回答する。即時にすべてのJWTが無効化されるとは限らない。バックアップ・ログは保持サイクル、識別不能な集計は集計として扱う。Google側連携解除はGoogleの管理画面、端末のゲスト戦績は端末側で別途管理する。非開示や対応困難な場合もその範囲・理由を回答する。本番の削除試験は行っていない。[Supabaseのユーザー管理](https://supabase.com/docs/guides/auth/managing-user-data)

**国外処理・同意。** サービス別の契約調査と残る法的判断は末尾の追補を参照。 DBは東京、Web関数は米国。CDN、バックアップ、事業者サポート、メール配送まで日本に限定できる証拠はない。本人から取得し自ら利用する各社のサービス、運営者による委託、その国外再委託は実際の契約・アクセス可能性で整理する。公開DPAの存在だけで個別契約の成立や相当措置を確定しない。委託先ごとに契約主体、取扱国、アクセス権限、保護措置、定期確認方法を記録する。外国第三者提供に当たり同意を根拠にする場合は国・当該国の制度・受領者の措置等について必要な情報を提供してから取得する。相当措置を根拠にする場合は継続確認と本人から求められた情報提供に対応する。[個人情報保護委員会・外国第三者提供編](https://www.ppc.go.jp/personalinfo/legal/guidelines_offshore/)・[Supabase DPA](https://supabase.com/legal/customer-resources/data-processing-addendum)・[Vercel DPA](https://vercel.com/legal/dpa)・[Vercelのリージョン](https://vercel.com/docs/regions)

**端末情報・広告。** ログイン用Cookie、端末内のゲスト・表示設定と、Cookieを用いない現行解析を区別した。現状の実装確認では、広告向けの同意バナーを新設する根拠はなかった。日本の外部送信規律の対象性はサービス類型、送信先・情報・用途で確認し、対象なら通知・公表等の適法な方法を選ぶ。他地域に向けた提供や広告開始は別途判定する。配信開始前にGoogleパブリッシャーポリシー、表示内容、送信先、ユーザー選択、配信地域を点検し、EEA・英国・スイスのパーソナライズド広告には該当する認定CMP要件を満たす。[電気通信事業法27条の12](https://laws.e-gov.go.jp/law/359AC0000000086)・[Googleの同意管理要件](https://support.google.com/adsense/answer/13554116?hl=ja)
